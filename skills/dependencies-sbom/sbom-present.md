## What this checks
The repository publishes a software bill of materials, either committed to the repository or generated by CI.

## How to evaluate
Look for committed SBOM files (SPDX or CycloneDX JSON or XML, `bom.json`, `sbom.json`, or an `sbom/` folder), or a CI workflow that generates one (Anchore `sbom-action`, Syft, CycloneDX, Microsoft `sbom-tool`, or GitHub's dependency graph export).

## Pass criteria
A committed SBOM or an SBOM-generating CI step exists.

## Fail criteria
Neither exists.

## How to fix
Commit `sbom/sbom.spdx.json`. Prefer GitHub's dependency graph export (`GET /repos/{owner}/{repo}/dependency-graph/sbom`). If it is empty, or the scanned branch isn't the default branch, generate an SPDX 2.3 document from the manifests and lockfiles fetched through the API. Also suggest adding a CI step that regenerates the SBOM on each release, so it doesn't go stale.
